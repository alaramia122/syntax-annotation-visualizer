# Правила валидации входного документа

**Статус:** утверждено вместе с контрактом v1.0. Структурные правила выполняет `schemas/annotation.schema.json`, межполевые — `src/annotation_validator.py`. Коды ниже относятся к семантическому валидатору.

## Структурная валидация

- Корректный синтаксис JSON и кодировка UTF-8.
- Корень — объект с обязательными `schema_version`, `document`, `analysis`.
- `schema_version` равен `"1.0"`.
- Обязательные поля и типы заданы схемой. Лишние поля запрещены (`additionalProperties: false`).
- `analysis.status` — только `complete` или `partial`.
- `kind` токена — только `word` или `punctuation`.
- Координаты в JSON — неотрицательные целые. Логическое значение `true`/`false` не является целым и отклоняется схемой.
- Непустые строки там, где схема задаёт `minLength: 1` (`id`, `language`, `lemma`, `pos`, `role`, `relation`, имя анализатора).

Отдельного поля с поверхностной формой токена в контракте нет. Форма всегда равна `text[start:end]`.

## Семантическая валидация

| Код | Правило |
|---|---|
| `duplicate_sentence_id` | Идентификаторы предложений уникальны в документе. |
| `duplicate_token_id` | Идентификаторы токенов уникальны в документе. |
| `sentence_range` | Для предложения `0 <= start <= end <= len(text)`. Пустой диапазон допустим. |
| `sentence_order` | Диапазоны предложений идут по неубыванию `start` и не пересекаются. Промежутки между предложениями допустимы. |
| `token_range` | Для токена `0 <= start < end <= len(text)`. |
| `token_order` | Токены в массиве упорядочены по `start`. |
| `overlapping_token_ranges` | Диапазоны токенов не пересекаются. Промежутки допустимы. |
| `unknown_sentence` | `sentence_id` ссылается на существующее предложение. |
| `token_outside_sentence` | Диапазон токена целиком внутри диапазона его предложения. |
| `empty_token_surface` | Поверхность токена не пустая и не состоит только из пробельных символов. |
| `whitespace_in_word_surface` | У токена `kind: "word"` внутри диапазона нет пробельных символов. Для пунктуации пробел внутри диапазона не запрещён отдельно, но поверхность только из пробелов запрещена. |
| `unknown_head` | Строковый `head` ссылается на существующий токен. |
| `cross_sentence_head` | Головной токен принадлежит тому же предложению. |
| `self_head` | Токен не ссылается на себя. |
| `head_cycle` | Цепочка `head` длиннее самоссылки не образует цикл. |
| `root_head` | `relation: "root"` требует `head: null`. |
| `missing_head` | Непустое `relation`, отличное от `root`, требует строковый `head`. |
| `incomplete_complete_analysis` | При `status: "complete"` у каждого токена `kind: "word"` есть непустой `syntax.role`. Для пунктуации роль не обязательна. При `partial` роль слова может отсутствовать. |

Несколько корней и отсутствие корня допустимы. Контракт не требует ровно одного корня на предложение: неполная разметка и несколько независимых узлов не должны отвергаться догадкой о структуре дерева.

`head: null` без `relation` допустим и не превращается автоматически в `root`. Неизвестные `role` и `relation` сохраняются как есть.

## Ошибки

Сообщения указывают путь в документе (`$.analysis.tokens[0]` и аналогичные). Некорректный документ не должен приводить к необработанному исключению на границе загрузки. Разбор JSON и отказ при слишком большом файле относятся к веб-слою и не являются критерием этапа 1.

## Безопасность

- Ограничить размер загружаемого файла на границе приложения.
- Не выполнять HTML/JavaScript из исходного текста и полей разметки.
- Проверять границы и типы перед обращением к данным.
- Не помещать секреты и пользовательские файлы в публичный репозиторий.
