# Формат входных данных

**Статус:** контракт v1.0 утверждён. Критерий приёмки выполнен локальными тестами: все файлы `examples/valid/*.json` проходят JSON Schema и семантическую проверку, каждый файл `examples/invalid/*.json` отклоняется ожидаемым слоем (схема или конкретный семантический код). См. `tests/test_fixtures.py`.

## Обязательная структура

Корневой объект содержит:

- `schema_version` — строка версии, для первой версии `"1.0"`;
- `document` — объект с `id`, `language`, `text`;
- `analysis` — объект с `status`, `sentences`, `tokens`.

`analysis.status` принимает `complete` или `partial`. `analysis.analyzer` — необязательные сведения об анализаторе (`name`, необязательная `version`).

`document.language` — непустая строка. Контракт не ограничивает её перечислением и не отклоняет значение, отличное от `ru`: приложение предназначено для русскоязычных текстов, но язык документа объявляется данными, а не угадывается.

Каждое предложение содержит уникальный `id` и целочисленные координаты `start`, `end`.

Каждый токен содержит уникальный `id`, координаты `start`, `end`, `kind` (`word` или `punctuation`) и `sentence_id`. Необязательные поля: `lemma`, `pos`, `features`, `syntax`.

Поверхностная форма токена отдельно не передаётся. Она всегда равна срезу `document.text[start:end]`.

`syntax` может содержать:
- `role` — синтаксическая роль;
- `head` — идентификатор головного токена либо `null`;
- `relation` — тип синтаксического отношения.

Для корня используется `relation: "root"` и `head: null`. Значения ролей и отношений не ограничиваются жёстким перечислением схемы: приложение должно сохранять незнакомые значения, не придумывая их трактовку. Несколько узлов без головы допустимы; ровно один корень на предложение не требуется.

## Семантика текста и координат

- Исходный текст — канонический источник символов, пробелов, пунктуации и переносов строк.
- Координаты — целочисленные Unicode-кодовые точки Python (`unicode_codepoints`).
- Интервалы полуоткрытые: `[start, end)`, эквивалентные Python-срезу `text[start:end]`.
- Синтаксическая роль может отсутствовать у слова при `status: "partial"`.
- Пунктуация остаётся в исходном тексте вне зависимости от того, описана ли она отдельными токенами.
- Токены должны ссылаться на существующие предложения, а головные токены — на существующие токены того же предложения.
- Семантическая валидация проверяет границы координат, уникальность ID, порядок и отсутствие пересечений диапазонов токенов/предложений, непустые поверхности токенов, отсутствие пробелов внутри словесных токенов, вложенность токенов в предложения, согласованность ссылок и отсутствие циклов в цепочках `head`.
- Промежутки между диапазонами токенов и предложений допустимы: пробелы, переносы строк и неразмеченные фрагменты сохраняются в исходном тексте и не требуют фиктивных токенов.
- Значение `complete` означает, что у каждого токена `kind: "word"` должна быть синтаксическая роль. Если хотя бы у одного слова роль отсутствует, следует использовать `partial`. Для пунктуации роль не обязательна и при `complete`.

Полный перечень кодов — в [правилах валидации](validation-rules.md).

## Разделение проверок

JSON Schema (`schemas/annotation.schema.json`) проверяет форму документа, обязательные поля, типы и простые ограничения. Модуль `src/annotation_validator.py` проверяет межполевые ограничения, которые неудобно выражать JSON Schema.

Необходимо сохранять различие между структурной ошибкой и семантической ошибкой. Приложение не должно показывать невалидный документ как полностью корректный.

## Соответствие требованиям ТЗ

К контракту этапа 1 относятся раздел 5 ТЗ и **FR-03** (обязательные поля, типы, координаты, порядок токенов, ссылки). Остальные функциональные требования описывают интерфейс и проверяются на следующих этапах; формат их не подменяет.

| Требование | Как закреплено |
|---|---|
| Обмен в JSON | Корень — объект контракта v1.0 |
| Текст первичен, его нельзя собирать из токенов | `document.text` каноничен; у токена нет отдельной поверхности |
| Координаты `unicode_codepoints` | Полуоткрытые интервалы Python; JavaScript переводит их в UTF-16, см. [coordinates.md](coordinates.md) |
| FR-03, проверка полей, типов, координат, порядка и ссылок | JSON Schema плюс семантические коды из правил валидации |
| FR-08, одинаковые словоформы остаются разными элементами | Разные токены с разными `id` и диапазонами; поиск по форме — не часть контракта |
| FR-18, неизвестное не подменяется | Нет обязательной леммы, части речи и роли при `partial`; незнакомые `role`/`relation` сохраняются |
| Неполный анализ | `analysis.status: "partial"` |
| Приложение не анализирует текст само | Валидатор не восстанавливает роли и не чинит ссылки |

Не входят в контракт v1.0 и не блокируют этап 1: графические линии, карточка, поиск, словарный источник, лимит размера файла на веб-границе, время отклика на 10 000 символов.

## Примеры

Валидные и невалидные фикстуры находятся в `examples/valid/` и `examples/invalid/`. Ожидаемый результат каждого невалидного файла записан в `tests/test_fixtures.py`. Они покрывают частичную разметку, пустой документ, Unicode вне BMP, переносы строк и промежутки между предложениями, грамматические признаки, повторяющиеся идентификаторы, координаты, порядок, пересечения, пробелы внутри слова, ссылки и циклы головных токенов.
