# Техническое задание

**Проект:** «Веб-приложение для визуализации синтаксической разметки русскоязычных текстов»  
**Дисциплина:** «Теория разработки программного обеспечения»  
**Версия исходного ТЗ:** 1.0

> Этот файл фиксирует требования из исходного документа ТЗ, предоставленного для проекта. Перед выпуском необходимо проверить, что все разделы исходного документа представлены полностью; при расхождениях исходный файл имеет приоритет.

## 1. Назначение и цель

Приложение предназначено для наглядного отображения результатов синтаксического анализа русского текста. Пользователь загружает документ с текстом и готовой синтаксической разметкой. Приложение отображает текст с графическими обозначениями членов предложения.

При выборе слова показываются доступные лингвистические сведения, синтаксическая роль, другие употребления словоформы или леммы в текущем тексте с группировкой по ролям, а также словарная справка при наличии доступного источника.

Приложение **не выполняет самостоятельный синтаксический анализ**. Его задачи — обработка входных данных, проверка, визуализация и предоставление контекстной информации.

## 2. Область разработки

### Входит в объём

- серверная обработка на Python;
- веб-интерфейс на HTML и CSS, интерактивность на JavaScript;
- загрузка JSON с синтаксической разметкой и демонстрационный документ;
- проверка структуры, типов, координат и ссылок;
- отображение предложений и слов;
- графическое обозначение синтаксических ролей преимущественно линиями;
- карточка слова и поиск употреблений;
- словарная/справочная функция с обработкой недоступности источника;
- функциональное и автоматизированное тестирование.

### Не входит в первую версию

- собственный алгоритм синтаксического анализа и автоматическое определение членов предложения;
- обучение языковых моделей;
- создание большой собственной лингвистической базы;
- пользовательские аккаунты и авторизация;
- совместное редактирование;
- хранение истории документов между сеансами;
- интеграция с графическими редакторами и сторонними системами разметки.

## 3. Пользовательские сценарии

1. **Загрузка:** пользователь загружает JSON или открывает демонстрационный пример. Система проверяет документ и при успехе показывает текст с разметкой; при ошибке выводит понятное сообщение и по возможности место ошибки.
2. **Карточка слова:** пользователь выбирает слово, оно выделяется, открывается карточка с доступными данными и найденными употреблениями.
3. **Переход к употреблению:** выбор результата в карточке переводит к соответствующему месту исходного текста и выделяет его.
4. **Недоступность словаря:** основная визуализация и поиск продолжают работать; вместо статьи показывается сообщение о временной недоступности справки.

## 4. Функциональные требования

### 4.1. Загрузка и проверка

- **FR-01:** загрузка JSON установленного формата.
- **FR-02:** открытие демонстрационного документа.
- **FR-03:** проверка обязательных полей, типов, координат, порядка токенов и ссылок между элементами разметки.
- **FR-04:** понятные сообщения об ошибках; некорректный документ не должен аварийно завершать приложение.

### 4.2. Отображение исходного текста

- **FR-05:** исходный текст отображается без изменения содержания.
- **FR-06:** сохраняются пробелы, пунктуация, последовательность символов и переносы строк.
- **FR-07:** обозначения привязаны к соответствующим диапазонам исходного текста.
- **FR-08:** одинаково написанные слова в разных позициях остаются отдельными элементами.
- **FR-09:** корректное отображение русского текста и типичной пунктуации.

### 4.3. Графические обозначения ролей

- **FR-10:** преимущественно подчёркивания, а не заливка слов разными цветами.
- **FR-11:** различные типы линий: сплошные, двойные, волнистые, пунктирные и штриховые.
- **FR-12:** ограниченная сдержанная палитра; цвета могут объединять роли в смысловые группы.
- **FR-13:** легенда соответствия обозначений синтаксическим ролям.
- **FR-14:** нейтральное оформление ролей без специального обозначения.
- **FR-15:** различимость не только по цвету, в том числе при нарушениях цветовосприятия и в оттенках серого.

Конкретная таблица оформления фиксируется в реализации и не считается универсальным лингвистическим стандартом.

### 4.4. Карточка слова

- **FR-16:** выбор размеченного слова открывает карточку.
- **FR-17:** карточка содержит исходную словоформу, лемму и часть речи при наличии, синтаксическую роль, дополнительные грамматические признаки, другие употребления и словарную справку при доступности.
- **FR-18:** отсутствующие сведения не подменяются догадками; они скрываются либо обозначаются как неизвестные.
- **FR-19:** карточка закрывается или заменяется при выборе другого слова.

### 4.5. Поиск употреблений

- **FR-20:** поиск других употреблений выбранного слова в текущем документе.
- **FR-21:** два режима — точная словоформа и лемма, если она есть в разметке.
- **FR-22:** группировка результатов по синтаксическим ролям.
- **FR-23:** контекст в пределах предложения, роль и переход к месту в исходном тексте.
- **FR-24:** возможность сравнить роли при нескольких употреблениях.
- **FR-25:** явное сообщение об отсутствии других употреблений.

### 4.6. Словарная справка

- **FR-26:** отдельный модуль получения словарной информации.
- **FR-27:** выбор источника с учётом доступности, условий использования и API; в качестве желаемого источника рассмотреть ресурсы Национального корпуса русского языка.
- **FR-28:** при наличии подходящего API получать справку по лемме или словоформе и возвращать унифицированный формат.
- **FR-29:** если автоматическое получение невозможно, допускается ссылка на внешний поиск; она не считается полноценной словарной статьёй.
- **FR-30:** локальный словарь допускается при объёме не более 30 МБ и соблюдении условий распространения.
- **FR-31:** недоступность справки не нарушает остальные функции.
- **FR-32:** не выдавать придуманные определения за внешние данные; указывать источник, если он известен.

До реализации справочного модуля необходимо отдельно проверить доступность источника, условия доступа и возможность программного использования данных.

## 5. Требования к входным данным

- Формат обмена — JSON.
- Исходный текст является первичным источником символов и пробелов; разметка ссылается на его участки координатами.
- Нельзя восстанавливать текст объединением токенов.
- Для первой версии ТЗ задаёт целочисленные смещения в Unicode-кодовых точках Python (`unicode_codepoints`).
- Точные правила диапазонов, обязательные поля, связи и семантическая валидация должны быть закреплены в спецификации формата до реализации.

## 6. Нефункциональные требования и качество

- Корректная работа с русским текстом и Unicode.
- Безопасная обработка некорректных файлов и пользовательского содержимого.
- Отсутствие выполнения произвольного HTML/JavaScript из загруженного текста.
- Ограничение размера входных данных.
- Основная функциональность должна работать без внешнего словарного сервиса.
- Проверить производительность на тексте до 10 000 символов; фактические критерии времени отклика определить до приёмочных испытаний.
- Выполнить модульные, интеграционные, системные и регрессионные проверки.
- Не публиковать секреты и ненужные временные файлы.

## 7. Документация, релиз и итоговый отчёт

Документация должна включать назначение приложения, требования к окружению, установку и запуск, формат JSON, визуальные обозначения, работу с карточкой и поиском, ограничения и устранение распространённых проблем. Техническая документация описывает архитектуру, зависимости, интерфейсы компонентов, валидацию, тесты и выпуск.

Перед релизом необходимо проверить чистое окружение, зависимости, тесты, основные сценарии, документацию и GitHub Actions; определить версию, создать тег и оформить GitHub Release. После публикации проверить соответствие релиза проверенному исходному коду.

Итоговый отчёт должен соответствовать требованиям кафедры и содержать постановку задачи, анализ требований, формат данных, обоснование технологий, архитектуру, основные алгоритмы и интерфейс, результаты тестирования, примеры работы, ограничения, заключение и источники. Утверждения о функциональности и испытаниях должны подтверждаться фактическими результатами.

## 8. Итоговые критерии готовности

1. Формат входных данных документирован и проверяется автоматически.
2. Валидные документы загружаются, ошибки обрабатываются без аварийного завершения.
3. Исходный текст сохраняется без потерь.
4. Роли различаются графически и объяснены легендой.
5. Карточка слова показывает доступные сведения.
6. Поиск по словоформе и лемме и переходы к употреблениям работают.
7. Справочная функция работает в пределах возможностей источника; её отказ не ломает приложение.
8. Автоматизированные тесты и основные пользовательские сценарии выполнены.
9. Документация соответствует реализации.
10. Репозиторий не содержит секретов и временных файлов.
11. Релиз опубликован и соответствует проверенному состоянию.
12. Итоговый отчёт подготовлен по требованиям кафедры.

## 9. Управление изменениями

Существенные изменения оцениваются по влиянию на архитектуру, формат JSON, интерфейсы, тесты, документацию и сроки. Изменения формата данных, координат или интерпретации ролей сопровождаются обновлением спецификаций и тестов. При расхождении ТЗ и реализации необходимо зафиксировать причину, решение и результат проверки.
