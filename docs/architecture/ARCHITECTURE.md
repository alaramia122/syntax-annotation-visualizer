# Архитектура приложения

## Статус документа

Начальная архитектурная заготовка. Окончательные решения принимаются после формализации JSON-контракта и проверки требований.

## Целевая схема ответственности

1. **Веб-слой (Flask):** маршруты, приём файла, вызов прикладных функций, формирование ответов и отображение ошибок.
2. **Модуль входных данных:** ограничение размера, безопасный разбор JSON, структурная и семантическая валидация.
3. **Модель аннотации:** единое представление документа, предложений, токенов и синтаксических ролей.
4. **Сервис контекста слова:** карточка токена, поиск по словоформе/лемме, группировка и навигация.
5. **Справочный адаптер:** изолированный интерфейс к внешнему/локальному источнику; отказ адаптера не должен ломать остальное приложение.
6. **Клиентский интерфейс:** HTML/CSS для представления, JavaScript для выбора токенов, карточки и переходов между употреблениями.
7. **Тесты:** модульные тесты доменной логики и валидации, интеграционные тесты веб-слоя, сквозные сценарии.

## Архитектурные ограничения

- Не выполнять синтаксический анализ текста.
- Сохранять исходный текст как первичный источник символов и пробелов.
- Не использовать пользовательский текст как доверенную HTML-разметку.
- Не связывать основную функциональность с доступностью словарного сервиса.
- Не добавлять инфраструктуру и зависимости без доказанной необходимости.

## Открытые решения

- Точный формат JSON и семантика связей.
- Граница между серверной и клиентской обработкой координат.
- Механизм наложения визуальных линий при пересекающихся синтаксических диапазонах.
- Конкретный источник словарной справки и его правовые/технические условия.
