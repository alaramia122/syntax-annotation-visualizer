# Инструкции для разработчиков и AI-агентов

## Цель

Продолжать разработку «Визуализатора синтаксической разметки» с любого этапа, используя репозиторий как основной источник контекста. Не полагаться исключительно на историю чата.

## Перед началом задачи

1. Прочитать этот файл и `docs/development/CURRENT_STATE.md`.
2. Для задач по требованиям свериться с `docs/requirements/ТЗ.md` и `docs/development/DEVELOPMENT_PLAN.md`.
3. Изучить относящиеся к задаче спецификации, архитектуру, решения (ADR/журнал решений), код и тесты.
4. Проверить состояние Git и не затирать чужие изменения.
5. Установить, какие критерии приёмки применимы к задаче.

## Правила разработки

- Не реализовывать самостоятельный синтаксический анализ: входной документ уже содержит разметку.
- Исходный текст является каноническим источником символов, пробелов, пунктуации и переносов строк. Не собирать его из токенов.
- Не придумывать отсутствующие лингвистические сведения. Неизвестные значения сохранять как неизвестные/отсутствующие согласно спецификации.
- Проверять данные на границах системы; ошибочный документ не должен приводить к необработанному падению приложения.
- Не вставлять пользовательский текст как доверенный HTML. Предотвращать выполнение HTML/JavaScript из загружаемого документа.
- Не добавлять зависимости и функциональность без необходимости и обоснования.
- Не считать успешный запуск единственным доказательством корректности: выполнять релевантные тесты.
- Не заявлять о выполнении проверки, публикации, релизе или исправлении без фактического подтверждения.
- При изменении формата JSON, координат, семантики ролей или интерфейсов обновлять спецификации и тесты.
- Не помещать секреты, токены и локальные конфигурации в репозиторий.

## Процесс выполнения

1. Сформулировать ожидаемый результат и критерии приёмки.
2. Изучить существующую реализацию и зависимости.
3. Внести минимально достаточные изменения.
4. Добавить или обновить тесты.
5. Запустить релевантные проверки и зафиксировать точные результаты.
6. Обновить документацию, если изменилось фактическое поведение или принято проектное решение.
7. Обновить `docs/development/CURRENT_STATE.md`: завершённые задачи, коммит/PR при наличии, тесты, известные проблемы и следующий конкретный шаг.
8. В итоговом сообщении разделить сделанное, проверенное, непроверенное и оставшееся.

## Статусы

Использовать явные формулировки:
- **Запланировано** — ещё не реализовано.
- **Реализовано** — код или документ создан, но проверки могут быть не завершены.
- **Проверено** — выполнены указанные проверки с известным результатом.
- **Заблокировано** — указана конкретная причина и необходимое действие.

## Работа с GitHub

- Предпочитать небольшие логически связанные коммиты.
- Для существенных изменений использовать ветку и Pull Request, если это не противоречит согласованному порядку работы.
- Не выполнять force-push, удаление веток, слияние или выпуск релиза без явной необходимости и полномочий.
- Проверять итоговое состояние после записи.
